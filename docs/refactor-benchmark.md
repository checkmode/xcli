# 重构期间的 HTTP 初步对照

这是一轮开发期测量，用来发现差异，不能代表完整产品性能。测试使用合成用户和本机回环流量，没有读取或访问生产用户数据。新版本尚未完成，数值也不能作为香港上线验收。

## 方法

- 测试环境：Ubuntu 26.04.1 LTS、Linux 7.0.0、x86-64，处理器为 AMD EPYC 9655。测试进程固定在一个可用 CPU 上，并以 `nice 19` 运行；该主机仍有其他工作负载，未获得独占资源。
- 旧版为 C++ Release 面板，使用 `--offline --no-auto-backup`；新版为 Rust Release 面板和 Node.js 26.7.0 接入层，未启动核心控制、自动备份或其他后台服务。Rust 编译器为 1.99.1。
- 两侧使用同一份合成数据库副本，包含 20 位用户；选中的用户使用独立服务分组。每个请求新建一个本地 HTTP 连接；每轮测试有 2 个并发请求、40 次请求；每个版本在每种顺序中测试两轮，并先分别预热 8 次。
- 测试分别按旧→新→新→旧及新→旧→旧→新运行，两个顺序各使用一套新建的合成进程和数据。用户链接接口的 JSON 在对照前逐项比对，Clash 配置逐字节比对；测量期间每个响应还要通过哈希校验。
- 只测量 HTTP 接入与配置生成，不包含 Nginx、TLS、公网延迟、真实 Clash 或小火箭、Xray 转发和流量记账。数据库和请求量较小，不能推断高并发、长时间负载或故障行为。
- RSS 为每轮结束时各被测进程的常驻内存之和；新版本将 Node 与 Rust 相加。进程间共享页可能被重复计算，不能直接视为整机实际内存增量。CPU 时间以 Linux 时钟粒度计量，短轮次只能粗略参考。

## 结果

延迟单位为毫秒；每个数字对应 80 次请求，不应将两次独立运行当作更大样本直接合并。

| 场景 | 顺序 | 版本 | P50 | P95 | 请求/秒 | 每请求 CPU 毫秒 | 观测 RSS 合计 MiB |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: |
| 用户订阅链接 | 旧→新→新→旧 | C++ | 1.506 | 2.384 | 1253.4 | 0.625 | 27.9 |
| 用户订阅链接 | 旧→新→新→旧 | Node + Rust | 1.611 | 2.846 | 1083.3 | 0.875 | 75.9 |
| 用户订阅链接 | 新→旧→旧→新 | C++ | 1.495 | 2.350 | 1276.7 | 0.625 | 28.1 |
| 用户订阅链接 | 新→旧→旧→新 | Node + Rust | 1.587 | 2.980 | 1048.4 | 0.750 | 75.5 |
| Clash 配置 | 旧→新→新→旧 | C++ | 2.664 | 4.215 | 718.2 | 1.250 | 30.5 |
| Clash 配置 | 旧→新→新→旧 | Node + Rust | 2.144 | 3.540 | 799.6 | 1.000 | 84.6 |
| Clash 配置 | 新→旧→旧→新 | C++ | 2.812 | 4.302 | 700.0 | 1.125 | 30.7 |
| Clash 配置 | 新→旧→旧→新 | Node + Rust | 2.191 | 3.626 | 792.7 | 1.000 | 84.1 |

两个顺序下，Clash 配置生成的延迟和请求速率均对新版有利；用户链接接口则略慢，新版两进程的 RSS 总和明显更高。这个结果只支持上述小负载场景，不能证明重构整体更快或更稳定。

## 工具与后续验收

可在隔离 Linux 环境使用 [benchmark_http.py](../tests/rewrite/benchmark_http.py)，分别传入 `--legacy`、`--panel`、`--node`、`--gateway` 四个测试文件路径，并以 `--order abba` 和 `--order baab` 运行。脚本仅创建临时数据，固定一个可用 CPU，停止自身启动的进程后删除临时目录；应由调用方设置低优先级。不要将生产数据库、密钥或服务路径传入脚本。
